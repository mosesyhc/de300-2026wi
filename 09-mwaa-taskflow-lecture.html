MWAA and Taskflow

Why MWAA - Managed Workflow Apache Airflow?

Apache Airflow orchestrates workflows as DAGs.

  • Scheduling + dependencies
  • Retries + backfills
  • Observability
  • Extensible operators/hooks

. . .

MWAA reduces ops burden:

  • Managed scheduler/webserver/workers
  • S3 for DAGs
  • CloudWatch logs
  • IAM + VPC integration

Airflow Components

Notes:

  • Webserver renders state from the metadata DB.
  • Scheduler parses DAGs and enqueues runnable tasks.
  • Workers pull tasks from the queue and execute them.

MWAA: Managed Airflow on AWS

Notes:

  • MWAA pulls DAGs/plugins/requirements from S3.
  • Logs stream to CloudWatch.
  • IAM controls AWS access; VPC controls networking.

DAGs as Graphs

A DAG is a directed acyclic graph:

  • Nodes = tasks
  • Edges = dependencies
  • No cycles

. . .

. . .

Notes:

  • Airflow enforces dependency order and handles retries/failures per task.

TaskFlow API (Modern Airflow)

TaskFlow is essentially Pythonic DAG authoring:

  • @dag defines the DAG
  • @task defines tasks as functions
  • Return values become XComs automatically

. . .

. . .

Notes:

  • With TaskFlow, your wiring is function calls + returned objects.

Demo DAG

We’ll build a minimal DAG that still feels production-ish:

  • scheduled (@daily)
  • params (runtime configuration)
  • retries
  • automatic XCom passing
  • branching
  • logs

Code: DAG + Params

from airflow.decorators import dag, task
from airflow.utils.dates import days_ago
from airflow.models.param import Param
from airflow.operators.python import get_current_context
import random
import logging

@dag(
    schedule="@daily",
    start_date=days_ago(1),
    catchup=False,
    tags=["mwaa", "taskflow", "demo"],
    params={"multiplier": Param(2, type="integer")},
)

...

Notes:

  • catchup=False avoids backfilling by default.
  • params are visible in the Airflow UI and overrideable per run.

Code: Task 1 — Generate

    @task(retries=2)
    def generate_numbers():
        numbers = [random.randint(1, 10) for _ in range(5)]
        logging.info(f"Generated numbers: {numbers}")
        return numbers

. . .

Notes:

  • The return value is automatically pushed to XCom.
  • Retries here maintain task-level resiliency.

Code: Task 2 — Transform with Context

    @task
    def multiply_numbers(numbers):
        context = get_current_context()
        multiplier = context["params"]["multiplier"]
        result = [n * multiplier for n in numbers]
        logging.info(f"Multiplied result: {result}")
        return result

. . .

Notes:

  • Pull DAG params at runtime via context.
  • This pattern is common for tuning behavior per run.

Code: Task 3 — Branch

    @task.branch
    def choose_path(numbers):
        total = sum(numbers)
        logging.info(f"Total sum: {total}")
        return "large_total" if total > 50 else "small_total"

. . .

Notes:

  • @task.branch performs true branching: non-chosen downstream tasks are skipped.

Code: Task 4 — Outcomes + Wiring

    @task
    def large_total():
        logging.info("Sum is large")

    @task
    def small_total():
        logging.info("Sum is small")

    nums = generate_numbers()
    multiplied = multiply_numbers(nums)
    decision = choose_path(multiplied)

    decision >> [large_total(), small_total()]

Notes:

  • Function calls define dependencies.
  • Values flow through XCom automatically.
